# 第三方数据接入需求（拉取与推送）

## 1. 文档定位

本文是工程数据驾驶舱接入外部业务系统的需求基线，覆盖两种方向：

1. 外部系统提供 API，驾驶舱主动调用并展示数据。
2. 驾驶舱提供接收接口，外部系统主动推送数据。

本文先定义业务边界和可验收的系统行为，再决定具体代码、表结构和部署方式。文中标记如下：

| 标记 | 含义 |
| --- | --- |
| 已实现 | 当前代码已有对应能力，仍须结合下列证据层级判断是否可上线 |
| 本地已验证 | 已由隔离服务、数据库或登录浏览器回归验证，不代表第三方或生产环境已通过 |
| 需补齐 | 需求中仍需新增、扩展或补充验证，当前代码不能直接承诺 |
| 待确认 | 必须由业务方、外部系统方或运维在实施前确认 |

默认使用 HTTPS；业务查询和推送优先采用 JSON。经明确登记的媒体查询可以使用受控表单请求和二进制响应，但仍须由服务端完成鉴权、校验和权限控制。外部系统仍是业务数据的权威来源，驾驶舱负责受控接入、标准化、查询和可视化，不承接外部系统的业务录入、审批和主数据维护。

每个具体来源还应形成独立的接口适配评审，记录来源实际路径、字段、认证、数据范围、阻断项和验收证据；来源要求的动态签名、业务成功标识、媒体查询或特殊响应类型一旦纳入范围，就应提升为该来源的 MVP，不能按通用扩展项默认后置。

第 3 至第 5 节是与来源无关的通用需求，第 6 节记录本平台当前代码基线，第 7 节提供实施前核对清单，第 8 节提供可复制的来源评审模板。第 6 节的实现状态不能替代具体来源的接口契约，也不能把规划能力写成已实现。

## 2. 两种场景的边界

| 项目 | 场景一：我方主动拉取 | 场景二：第三方主动推送 |
| --- | --- | --- |
| 数据流向 | 外部系统 → 驾驶舱请求 → 外部系统响应 | 外部系统请求 → 驾驶舱接收接口 |
| 触发方 | 驾驶舱按页面/组件刷新或人工测试触发 | 外部系统按事件、快照完成、批次或文件通知触发 |
| 驾驶舱职责 | 保存来源配置，调用、解析、限流并展示 | 鉴权、校验、幂等接收、持久化、处理和回执 |
| 数据落点 | 可以直接形成数据集结果，也可以落入本地标准表 | 必须先可靠接收；建议进入队列和标准表后供数据集读取 |
| 实时展示 | 当前以轮询为主；可由平台 WebSocket 向浏览器推送结果 | 接收后可通过 Redis/消息队列通知平台 WebSocket，或由页面轮询标准表 |
| 失败重试主责 | 驾驶舱负责调用重试和状态记录 | 外部系统根据回执负责投递重试，驾驶舱负责幂等和死信处理 |
| 当前系统状态 | 来源、endpoint、数据集投影、动态签名、JSON/表单请求、媒体代理、有限重试与断路已实现并完成隔离回归；通用分页和跨数据集共享原始抓取已补齐；真实来源联调仍待完成 | 版本化接收、HMAC 防重放、幂等批次、标准化记录、状态查询和死信重放已实现并完成单实例隔离回归；多实例消费租约、站内告警和下游页面更新已补齐；真实推送方联调仍待完成 |

以下“实时”指业务数据从来源到页面的可接受延迟，具体目标必须按业务场景确认，不能只以连接建立成功作为实时接入证据。

## 3. 共享业务要求

### 3.1 来源、endpoint、数据集和页面分层

- 数据源保存连接地址、协议、认证信息和网络约束；endpoint 保存稳定路径、方法、请求/响应类型和认证策略；数据集保存请求/响应映射、字段和参数；页面只引用数据集编码和绑定字段。
- 页面 JSON 不保存 URL、令牌、请求头、数据库密码或第三方签名密钥。
- 出站连接统一使用稳定的 `sourceCode`，同一连接下的 `endpointCode` 唯一；数据集保存 `sourceCode + endpointCode` 复合引用（旧实现中的 `dataSourceCode` 只作兼容映射）。入站接入方统一使用 `integrationCode`，不得与出站来源编码混用。
- 来源编码、endpoint 编码、数据集编码和页面编码是稳定引用，创建后不可随意修改；名称和备注可以维护。
- 数据集必须经历“草稿 → 测试通过 → 启用 → 页面发布”流程。停用来源或数据集后，运行页面显示明确状态，不把失败当成数值 0。
- 每次取数或接收都生成平台 `requestId`；出站来源和入站接入方使用明确的命名空间。入站消息按 profile 使用业务主键（例如 `EVENT` 的 `eventId`、`SNAPSHOT` 的 `snapshotId`），便于从页面结果追溯到原始请求或投递记录。

### 3.2 权限和责任

| 角色 | 职责 |
| --- | --- |
| 业务负责人 | 确认字段含义、业务范围、时间口径、数据保留和敏感字段 |
| 外部系统负责人 | 提供接口契约、测试环境、账号/签名材料、网络白名单和重试规则 |
| 平台管理员 | 登记来源、配置数据集、执行测试、启用和发布页面 |
| 运维/集成管理员 | 管理密钥、网络、证书、监控、失败重放和应急切换 |
| 页面查看者 | 只读取已授权的页面和结果，不接触来源凭证 |

新增的接入管理功能建议单独使用 `integration:*` 权限（按现有 RuoYi 约定实际加产品前缀）；现有数据源/数据集管理权限只授予需要配置平台数据的人员。第三方调用接收接口不使用平台后台账号登录。

### 3.3 时间、字段和数据质量

- 所有接口必须在来源登记中声明时区。平台默认时区只能作为可配置初始值，不能替代来源确认；时间传输优先采用带时区的 ISO 8601，使用无时区字符串时必须明确解释规则。
- 每条数据区分来源业务时间、来源发送时间、平台接收时间和页面抓取时间。
- 字段定义包含名称、显示标题、目标类型、是否展示、字典/枚举、脱敏规则和业务说明。字段定义用于绑定和展示，不能代替服务端数据裁剪或权限控制；类型转换必须明确空值、默认值、精度、溢出、未知枚举和行级错误处理。
- 拉取质量状态至少包括：`SUCCESS`、`NO_DATA`、`PARTIAL`、`TRUNCATED`、`NOT_CONNECTED`、`INVALID_CONFIG`、`INVALID_DATA`、`TIMEOUT`、`AUTH_ERROR`、`RATE_LIMITED`、`SOURCE_ERROR`、`CIRCUIT_OPEN`、`STALE`；入站消息状态另行使用 `RECEIVED`、`VALIDATED`、`PROCESSING`、`ACCEPTED`、`DUPLICATE`、`REJECTED`、`FAILED`、`DEAD_LETTER`、`CONFLICT`。
- 只有确认响应路径存在且数据通过 schema 校验时才可标记 `SUCCESS`；合法空数组标记 `NO_DATA`，截断或部分成功必须显式标记，鉴权、超时、格式或来源异常不得显示为业务数字 0。

### 3.4 安全和审计

- 出站来源默认使用端到端 HTTPS；兼容仅提供 HTTP 的第三方时，管理员可在该来源显式选择 `PUBLIC_HTTP`，并填写主机、端口白名单，正式环境无需开启开发开关。HTTP 不提供传输加密，签名只能验证请求身份。入站接收及回调仍按各自的加密链路要求配置。来源主机、端口、TLS SNI/证书主机、推送方 IP、平台入口和跨域 Origin 分别维护白名单；HTTPS 以 IP 访问时必须有匹配的证书 SAN 或登记的 SNI，禁止关闭证书校验。
- 出站地址和入站回调地址均须执行 SSRF 防护：校验协议、主机和端口，解析后阻断私网、链路本地、回环、IPv4-mapped IPv6、云元数据等地址，重定向和 DNS 变化重新校验。公网 `PUBLIC_HTTPS` 与 `PUBLIC_HTTP` 都阻断私网目标，前者仍强制 HTTPS；受控专网或隧道使用 `PRIVATE_LINK`、明确批准的 CIDR 和出口接口（仍阻断回环、链路本地和云元数据）。`PUBLIC_HTTP` 不回退到全局主机白名单，也不接受开发开关放行私网目标。
- 默认不跟随重定向；契约确有需要时逐跳校验协议、主机、端口和解析后的地址，限制最大跳数并禁止 HTTPS 降级。分页链接、媒体下载和 OAuth 回调分别登记重定向策略，不能共享一个“允许重定向”开关。
- 密码、令牌、API Key、HMAC 密钥和证书私钥只在服务端或密钥服务中保存，数据库仅保存加密值或外部密钥引用。
- 认证策略使用版本化受控 provider（例如 `NO_AUTH`、API Key、Bearer、HMAC、OAuth、mTLS）。`NO_AUTH` 只能用于已登记的公开只读来源，仍受所选网络策略、主机/端口白名单、限流和数据范围约束；不能以凭证为空代替显式 provider。需要凭证的 provider 都要登记凭证引用、认证主体、权限范围和轮换/吊销规则，签名 provider 另行登记时间单位、时钟偏差、规范化原文 profile、编码和请求头位置，mTLS 登记证书链/客户端证书，OAuth 登记 token 地址、scope、刷新/吊销和缓存隔离规则。签名 provider 按原始请求字节签名并在重试时重新签名，其他 provider 按各自协议重新认证；禁止脚本和任意请求头模板。
- 日志不得记录完整 Authorization、签名、原始敏感字段和完整请求体；路径、query、form、`mediaRef`、个人/设备/其他业务对象标识、消息 ID 等外部值按字段白名单限长和限字符，必要时只记哈希或脱敏值，并关闭 HTTP body tracing/APM 自动采集。调试样本必须脱敏并设置过期时间。
- 对配置变更、连接测试、启用/停用、人工重放、死信处理和密钥轮换记录操作者、时间、对象、结果及原因。
- 接口错误响应只返回可定位的错误码、简短消息和 `requestId`，不返回 SQL、内部主机、堆栈和密钥信息。

## 4. 场景一：第三方提供 API，我方主动取数

### 4.1 目标和适用范围

平台管理员登记一个外部 HTTP 来源，建立一个或多个 API 数据集，测试返回结构后绑定到指标、图表、表格或实时组件。数据可以是当前快照，也可以通过参数表达项目、组织、日期或增量范围。

适用方式包括：

- 查询型 GET 接口；
- 无请求体的受控 POST 查询接口；
- 返回 JSON 数组或 JSON 对象中嵌套数组的接口；
- 有明确总数、更新时间或业务日期的快照接口；
- 经登记的表单查询和受控二进制媒体响应。

来源要求的认证、业务成功规则、请求/响应类型和必要投影必须纳入对应项目的 MVP。任意脚本签名、文件上传、异步任务轮询、通用分页和跨来源聚合仍应单独评审；具体来源的特殊能力应在该来源适配评审中明确是否属于 MVP。

### 4.2 业务流程

1. 外部系统方提交接口说明、样例响应、认证方式和测试地址。
2. 业务负责人确认字段口径、项目/组织范围、时间语义、脱敏要求和刷新频率。
3. 平台管理员在“数据源管理”登记 HTTP 来源，填写基础地址、认证方式、服务端凭证引用和网络策略。
4. 在该来源下登记 endpoint，声明相对路径、方法、请求内容类型、响应类型和业务成功规则。
5. 平台执行来源及 endpoint 连接测试，确认主机白名单、TLS、认证、基本 HTTP 状态和业务成功标识。
6. 管理员新建 API 数据集，引用 `sourceCode + endpointCode`，声明参数、响应投影、字段转换和业务时间。
7. 使用脱敏样本执行数据集测试，核对行数、字段类型、总数和业务时间；测试结果写入测试状态。
8. 配置字段标题、展示规则、字典和组件绑定，保存草稿并发布页面。
9. 运行中按页面/组件刷新周期取数，异常时显示质量状态并记录请求 ID。

### 4.3 外部系统方必须提供的资料

| 资料 | 必填内容 |
| --- | --- |
| 接口地址 | 测试和生产地址、路径、DNS、TLS 证书链要求 |
| 请求契约 | 方法、查询参数、路径变量、是否需要请求体、请求头、编码 |
| 认证契约 | Bearer/API Key/Basic/HMAC/mTLS 等方式、轮换周期、失效响应 |
| 响应契约 | HTTP 状态、业务成功字段和值、成功和失败示例、数据数组路径、总数路径、更新时间路径、错误码 |
| 数据口径 | 字段定义、枚举、单位、时区、脱敏和数据权限范围 |
| 性能约束 | QPS、最大返回行数/字节数、超时建议、限流和维护窗口 |
| 增量规则 | 是否支持时间或游标参数、重复数据规则、历史修正方式 |
| 媒体契约 | 内容类型、允许格式、最大大小、引用有效期、缓存、权限、无内容和失败响应 |
| 联调条件 | 测试账号、测试项目、网络白名单、联系人和故障响应时间 |

### 4.4 来源配置需求

#### 管理员可配置字段

| 字段 | 通用要求 |
| --- | --- |
| 来源编码/名称 | 唯一、可检索、名称中文化 |
| 类型 | HTTP |
| 基础地址 | 页面不直接暴露；服务端校验协议、主机和端口白名单 |
| 认证信息 | 服务端保存 `credentialRef`/密钥引用；每个 endpoint 至少绑定一种受控认证 provider；公开来源也要显式登记 `NO_AUTH`，不能用空配置隐式放行 |
| 出站认证策略 | 固定凭证或审核过的动态签名策略；浏览器不得指定签名逻辑 |
| 静态请求头 | 仅允许契约登记的非敏感头；禁止覆盖 Host、代理和安全头 |
| endpoint 目录 | 一个来源登记多个稳定路径、方法、请求/响应类型和成功规则 |
| TLS/代理 | 证书校验、代理和超时由运维配置 |
| 状态 | 草稿、启用、停用 |

来源详情不得向浏览器返回完整地址或凭证。目标模型应把基础地址/认证与 endpoint 分开；部署环境再按平台实现配置主机白名单。

默认情况下 endpoint 继承所属来源的认证 provider 和凭证；只有来源契约明确要求时才允许 endpoint 级覆盖，并必须使用独立的 `credentialRef`、权限范围和审计记录。数据集和浏览器不能覆盖来源或 endpoint 的认证配置。

来源连接的目标结构示例（仅为字段示意，正式地址和密钥通过部署环境或密钥服务注入）：

```json
{
  "sourceCode": "external-source",
  "protocol": "HTTPS",
  "baseUrlRef": "EXTERNAL_SOURCE_BASE_URL",
  "networkProfile": "PUBLIC_HTTPS",
  "allowedHostsRef": "EXTERNAL_SOURCE_ALLOWED_HOSTS",
  "authProviderRef": "external-source-auth-v1"
}
```

#### endpoint 可配置字段

| 字段 | 需求 |
| --- | --- |
| endpoint 编码/名称 | 在来源内唯一，创建后稳定；用户可见名称使用通用业务说法 |
| 相对路径/方法 | 只能由管理员从已审核契约登记；禁止绝对 URL、重定向改主机和浏览器覆盖 |
| 请求类型 | `NONE`、受控 `JSON` 或 `FORM_URLENCODED`；字段只能绑定到声明参数 |
| 响应类型 | `JSON` 或受控 `BINARY_MEDIA`；媒体响应由专用代理处理，图片只是其中一种 profile |
| 业务成功规则 | `envelopeMode`、`successPath`/`successValue` 或 `codePath`/`successCodes`、`messagePath`、`errorCodePath` 和可重试错误码映射 |
| 质量路径 | 可选的 `partialPath`、`truncatedPath`、`retryAfterPath`；缺失时使用平台默认规则 |
| 容量策略 | 超时、最大响应体、最大行数、并发、QPS 和重试策略 |
| 状态/版本 | 草稿、启用、停用、契约版本和最后测试结果 |

认证和 endpoint 配置必须使用受控字段，不允许保存可执行脚本或任意请求头模板。动态签名在服务端实现为审核过的策略；每次重试按认证 provider 重新生成有时效的认证材料，签名 provider 重新签名。

认证 provider 采用版本化配置，示例字段如下：

```json
{
  "provider": "HMAC_V1",
  "credentialRef": "external-secret-ref",
  "identityRef": "external-app-key-ref",
  "keyId": "external-key-id",
  "algorithm": "HMAC-SHA256",
  "headerMapping": {
    "identity": "X-App-Key",
    "keyId": "X-Key-Id",
    "timestamp": "X-Timestamp",
    "nonce": "X-Nonce",
    "signature": "X-Signature"
  },
  "timestampUnit": "MILLISECONDS",
  "clockSkewSeconds": 300,
  "nonceRequired": true,
  "canonicalProfile": "METHOD_PATH_TIMESTAMP_NONCE_IDEMPOTENCY_SCHEMA_BODY_V1",
  "signatureEncoding": "BASE64"
}
```

`canonicalProfile` 只能引用受控策略标识，不能保存可执行模板或把换行写成字面反斜杠。推荐的 HMAC profile 将方法、规范化路径/查询串、身份、时间戳、`keyId`、nonce、幂等标识、schema 版本和原始请求体摘要按固定顺序纳入签名；实际是否包含每项由来源契约冻结。服务端使用 constant-time 比较签名，并拒绝未知算法、认证降级和浏览器指定的 provider。只有签名 provider 才按原始请求字节生成签名；固定 Bearer/API Key 不应被强行套用 HMAC。若来源未绑定 method、path、body、幂等标识或 nonce，适配评审必须将其列为高风险；完成加密链路、较短有效窗口、IP/权限限制和只读密钥等补偿控制，并经安全负责人书面接受后方可生产，未完成则阻断。同一来源的测试、生产凭证和轮换记录必须隔离。

#### 媒体策略

当 endpoint 的响应类型为 `BINARY_MEDIA` 时，必须登记独立媒体策略：

| 项目 | 通用要求 |
| --- | --- |
| 引用 | 浏览器只接收不透明的 `mediaRef`；不得提交任意 URL、上游路径或凭证 |
| 允许内容 | 明确允许的 MIME、文件头/魔数、扩展名和最大字节数；不能只信任上游 `Content-Type` |
| 下载控制 | 连接、首字节、完整下载超时、并发和重定向主机均受限；按流式大小上限中止 |
| 返回头 | 不直接透传上游文件名或 `Content-Disposition`；由平台按探测结果设置安全的媒体类型和 inline/attachment 策略，并设置 `X-Content-Type-Options: nosniff` |
| 生命周期 | `mediaRef` 绑定来源、业务记录和页面/分享版本，设置不超过来源引用有效期的 TTL；撤销权限时清理引用和缓存 |
| 权限审计 | 每次解析和下载检查页面/分享权限，记录来源、引用、操作者、结果和 `requestId`，不记录原始地址 |
| 内容风险 | 按数据敏感度选择病毒扫描、压缩炸弹/EXIF 处理和内容审查；失败返回稳定媒体错误，不缓存不可信内容 |

图片、视频、文档和音频都使用上述媒体策略；`pictureRef` 等名称只应作为具体来源的字段别名，通用接口统一使用 `mediaRef`。

媒体安全默认采用拒绝优先：除非契约明确允许，不接收 SVG、HTML、脚本、Flash 等可执行或可嵌入格式；对图片限制解码后的像素数、尺寸、动画帧和压缩展开量，校验通过后再去除 EXIF 并进入缓存。上游 `Content-Type`、文件名、`Location` 和 `Content-Disposition` 均不得直接透传；上游纯文本错误只保留内部限长脱敏摘要，不回显给浏览器。

来源返回的媒体参数（例如相对路径和服务器标识）必须在服务端校验为同一业务记录的成对值，只允许契约规定的相对路径、字符集和长度，拒绝 scheme、主机、`..`、控制字符和不在可信记录中的服务器标识；未通过页面/分享授权时，在调用上游前拒绝。平台对外只签发高熵、不可枚举的 `mediaRef`，绑定 `environment + sourceCode + 业务主键 + pageId/revisionId 或分享版本`、创建/失效时间和撤销状态，并按最短业务需求设置 TTL（不得超过来源引用有效期）；缓存命中仍需复核权限，撤销时立即失效引用和缓存。

媒体访问使用独立的受保护 endpoint，不接受任意 URL 或上游参数。登录页面可使用 `GET /dashboard/runtime/media/{mediaRef}`，匿名分享可使用独立的 `GET /public/share/{token}/media/{mediaRef}`；路径仅为需求示例，实际实现必须分别校验登录会话或分享令牌，并按 `pageId/revisionId` 或分享版本复核绑定，不能把 `/open-api` 当作无需鉴权的媒体入口。Range、下载和跨域行为按媒体 profile 明确，默认关闭 Range 和跨域；若契约允许分段读取，也必须逐段执行权限、字节上限和缓存校验。`FILE_NOTIFICATION` 中的 `mediaRef` 只能是平台预发的对象引用或预签名上传结果；外部 URL 一律拒绝。平台需要主动下载时，另行登记固定来源的文件传输 endpoint，并执行签名、白名单、逐跳 SSRF 和内容校验。

#### endpoint 配置示例

```json
{
  "sourceCode": "external-source",
  "endpointCode": "records",
  "path": "/v1/records",
  "method": "GET",
  "requestContentType": "NONE",
  "responseType": "JSON",
  "authProviderRef": "external-source-auth-v1",
  "envelopeMode": "JSON_BOOLEAN",
  "successPath": "success",
  "successValue": true,
  "messagePath": "message"
}
```

endpoint 路径、方法、请求/响应类型和认证 provider 由管理员按已审核契约登记；数据集只能引用这个复合 endpoint 标识，不能在运行请求中覆盖。

#### 数据集可配置字段

```json
{
  "sourceCode": "external-business",
  "endpointCode": "external-events",
  "params": [
    { "name": "projectCode", "in": "query", "type": "STRING", "required": true },
    { "name": "startTime", "in": "query", "type": "DATETIME", "required": false }
  ],
  "response": {
    "envelopeMode": "JSON_BOOLEAN",
    "successPath": "success",
    "successValue": true,
    "messagePath": "message",
    "rowsPath": "data.items",
    "totalPath": "data.total",
    "businessTimePath": "data.updatedAt"
  },
  "rowLimit": 100
}
```

使用 `JSON_CODE` 时，将 `successPath/successValue` 替换为该来源的 `codePath` 和 `successCodes`（允许的成功码数组）；`errorCodePath`、`retryAfterPath`、`partialPath`、`truncatedPath` 按来源响应实际字段登记，不应把不适用的路径填成默认值。例如：

```json
{
  "envelopeMode": "JSON_CODE",
  "codePath": "code",
  "successCodes": ["0", "OK"],
  "messagePath": "message",
  "rowsPath": "data.items"
}
```

`successCodes` 按来源实际 JSON 类型登记，数值码和字符串码严格区分，不做隐式字符串转换。

实际页面保存时，当前系统的 `paramSchemaJson` 是参数声明，`configJson` 保存接口和响应映射；上面的 `params` 仅作为需求示意，落地时需按现有字段模型拆分。

| 字段 | 需求 |
| --- | --- |
| `sourceCode + endpointCode` | 只引用同一来源下已登记、测试通过并启用的受控服务端 endpoint；不得跨来源串用同名 endpoint |
| `method` | 由 endpoint 决定；数据集不能覆盖 |
| 参数 | 参数名、位置、类型、必填、默认值、范围/枚举、编码和脱敏显示；未声明参数默认拒绝，只有契约明确时才忽略 |
| 路径/查询变量 | 仅使用 `in=path/query` 的声明参数；所有值按契约 URI 编码，禁止浏览器提交任意 URL |
| 请求体 | JSON/表单字段只能绑定到 endpoint 声明位置；普通页面不能构造二进制或上传请求 |
| 参数位置 | 每个参数必须声明 `in: path/query/header/json/form`；只发送声明位置，禁止把所有参数隐式追加到 query |
| 业务成功 | 按 endpoint 的 `envelopeMode`、`successPath/successValue` 或 `codePath/successCodes` 及错误映射判定，不能只判断 HTTP 2xx |
| 响应行路径 | 例如 `data.items`；根数组可以留空 |
| 总数/业务时间 | 可选路径，分别映射 `total` 和 `businessTime` |
| 字段投影 | 服务端白名单、别名、类型转换、枚举和脱敏；字段定义不能只作为前端展示提示 |
| 分页 | 首期明确采用单次请求；通用 page/size、游标或 Link 分页需单独实现 |
| 行数和字节上限 | 不超过平台上限；超限返回明确错误或 `truncated=true`，不得静默截断后仍显示完整成功 |
| 刷新/超时 | 页面和组件可配置；来源限流时显示 `RATE_LIMITED` |
| 重试 | 需求新增指数退避、最大次数和可重试状态白名单 |

参数位置只允许 `path`、`query`、`header`、`json`、`form`。服务端在发出请求前校验必填、类型、长度、枚举、正则和范围；缺失必填参数直接返回配置/参数错误。数组、日期、布尔值和空值的序列化规则写入 endpoint 契约；不允许通过参数覆盖 Host、代理、认证或签名头。路径表达式使用受限 JSONPath/点分隔语法，只允许读取声明的字段和数组索引，禁止脚本、过滤表达式和任意执行。

字段投影的目标类型至少包括 `STRING`、`INTEGER`、`DECIMAL`、`BOOLEAN`、`DATE`、`DATETIME`、`ENUM` 和受控 `JSON`。转换必须采用严格模式：非法值、溢出、精度超限、未知枚举和必填字段缺失按行标记 `INVALID_DATA`；只有来源契约允许时才可使用默认值或跳过该行。映射、字典和转换规则均需带 schema 版本，并保留旧版本的兼容期。

同一 endpoint 的多个投影应按“`sourceCode + endpointCode` + 规范化参数 + 认证策略/凭证版本 + schema 版本 + 环境 + 租户/页面/分享受众范围”生成 coalescing key，在同一刷新批次复用同一份原始响应、`requestId` 和抓取时间；命中共享结果时仍要复核授权。请求失败或响应过期时，关联投影整体失败或整体标记 `STALE`，不能由不同抓取结果拼接出一组看似一致的数据。

`envelopeMode` 必须显式选择。`HTTP_ONLY` 是无业务信封时的唯一模式，不另设等价的空模式，避免配置歧义：

| 模式 | 判定规则 | 缺失或不匹配时 |
| --- | --- | --- |
| `HTTP_ONLY` | HTTP 状态允许且响应 schema 合法即成功 | schema 或内容类型不合法时 `INVALID_DATA` |
| `JSON_BOOLEAN` | `successPath` 存在且严格等于配置的布尔 `successValue` | 缺失、`null` 或类型不符为 `INVALID_DATA`；值为失败为 `SOURCE_ERROR` |
| `JSON_CODE` | `codePath` 的值命中 `successCodes` 允许列表 | 缺失或未知码为 `INVALID_DATA`；已知失败码按错误映射处理 |
| `OPTIONAL` | 有信封时按已登记规则判断；无信封时按 `HTTP_ONLY` 和 schema 判断 | 出现信封但格式不完整时 `INVALID_DATA` |

判定顺序固定为“HTTP 状态 → 内容类型 → 业务信封 → schema/路径 → 字段投影”。响应解析同样执行字节、JSON 深度、字段数、数组长度和重复 key 限制；`messagePath`、`errorCodePath`、`retryableCodes` 和 `retryAfterPath` 只用于错误归类和重试决策，消息必须限长、脱敏；必需路径缺失不得变成 `NO_DATA`。

### 4.5 请求与响应契约

#### 通用 Bearer 来源请求示例

```http
GET /v1/events?projectCode=demo&startTime=2026-09-08T00%3A00%3A00%2B08%3A00 HTTP/1.1
Host: api.example.com
Accept: application/json
Authorization: Bearer <server-side-token>
```

`Authorization`、来源项目头和其他密钥由服务端注入。浏览器只提交页面、组件、数据集编码和已声明参数。

该示例只说明普通 Bearer 来源。若来源要求动态签名，应由 endpoint 的受控认证策略在服务端逐次生成请求头，不能让页面提交签名逻辑。

#### 推荐成功响应

以下仅以记录型 JSON API 为例，字段不构成强制 schema；实际字段、路径和类型由 endpoint 契约及数据集投影定义。示例采用 `JSON_BOOLEAN` 判定；若来源采用 `JSON_CODE`，必须按前述规则登记 `codePath` 和 `successCodes`，不能同时依赖两套成功判定。

```json
{
  "success": true,
  "message": "success",
  "requestId": "source-request-001",
  "data": {
    "items": [
      {
        "eventId": "E10001",
        "eventType": "IN",
        "occurredAt": "2026-09-08T09:58:00+08:00",
        "status": "NORMAL"
      }
    ],
    "total": 1,
    "updatedAt": "2026-09-08T10:00:00+08:00"
  }
}
```

平台需要把不同来源转换为统一结果：

```json
{
  "sourceCode": "external-business",
  "endpointCode": "external-events",
  "datasetCode": "external-events-dataset",
  "rows": [
    {
      "eventId": "E10001",
      "eventType": "IN",
      "occurredAt": "2026-09-08T09:58:00+08:00",
      "status": "NORMAL"
    }
  ],
  "total": 1,
  "businessTime": "2026-09-08T10:00:00+08:00",
  "quality": "SUCCESS",
  "sourceStatus": "CONNECTED",
  "sourceRequestId": "source-request-001",
  "requestId": "platform-request-001",
  "fetchedAt": "2026-09-08T10:00:01+08:00"
}
```

`quality` 表示本次数据结果，`sourceStatus` 只表示来源连接状态；`sourceRequestId` 是上游返回的追踪号，平台 `requestId` 始终由服务端生成，二者都不能替代鉴权或权限判断。

### 4.6 异常处理

| 情况 | 平台行为 | 是否建议外部重试 |
| --- | --- | --- |
| 2xx + 合法数据 | 返回 `SUCCESS`，记录行数和业务时间 | 按刷新周期再次读取 |
| 2xx + 空数组 | 返回 `NO_DATA`，不显示为 0 | 按业务刷新策略 |
| 2xx + 业务成功标识为失败 | `SOURCE_ERROR`，提取受限的来源消息摘要 | 按来源错误码确定，不能当成空数据 |
| 204 或合法空结果 | 按来源契约映射为 `NO_DATA`；不得把无响应体当成 schema 成功 | 按来源刷新策略 |
| 400/422 参数或契约错误 | 平台发出请求前参数/配置不合法时 `INVALID_CONFIG`；来源返回的业务拒绝为 `SOURCE_ERROR`；响应格式或字段不符合 schema 为 `INVALID_DATA`；保留稳定错误码和脱敏摘要 | 修正配置或按错误码决定 |
| 401/403 | `AUTH_ERROR`，告警但不泄露令牌 | 先更新凭证，不盲目重试 |
| 408/429 | `TIMEOUT`/`RATE_LIMITED`，遵守 `Retry-After` | 指数退避 |
| 5xx/网络失败 | `SOURCE_ERROR`，记录耗时和请求 ID | 按策略有限重试 |
| JSON 解析失败/路径不存在 | `INVALID_DATA`，阻止错误数据进入页面 | 修正契约或来源 |
| 部分行转换失败 | 按来源策略返回 `PARTIAL` 或整批 `INVALID_DATA`；逐行错误可追踪 | 仅在契约允许时重试失败行 |
| 响应或结果被上限截断 | `TRUNCATED`，记录实际/上限数量；不得伪装成完整 `SUCCESS` | 调整分页/容量或明确快照范围 |
| 二进制媒体类型、文件头或大小不合法 | `INVALID_DATA`，中止代理且不缓存 | 修正来源；不自动重试非法内容 |
| 主机不在白名单 | 配置阶段拒绝或返回 `INVALID_CONFIG` | 不重试 |

### 4.7 场景一验收标准

- 管理员可以登记、测试、启用和停用 HTTP 来源；地址和令牌不会出现在运行/分享结果、页面 JSON 或普通日志中；授权配置编辑入口可回显完整配置和凭证。
- 一个来源可以登记多个 endpoint；数据集只能引用已启用 endpoint，浏览器不能覆盖主机、路径、方法或认证策略。
- GET 查询可以正确传递声明参数；路径变量和查询参数完成 URI 编码，未声明参数不得发送，默认拒绝，只有契约明确允许时才忽略。
- 根数组、嵌套数组和对象单行都能按配置映射；同一响应可建立多个独立投影，关联投影可共享来源请求 ID 和抓取时间；总数、业务时间和字段类型与样例契约一致。
- HTTP 2xx 但业务成功标识为失败时返回来源错误；错误消息经过长度限制和脱敏。
- 空数据、鉴权失败、限流、超时、非 JSON、字段路径错误和主机白名单失败均显示可区分状态，并带 `requestId`。
- 需要媒体查询时，浏览器只使用平台不透明引用；服务端完成表单请求、鉴权、来源参数成对校验、文件类型/大小/解码像素校验和页面权限校验。
- 媒体验收还要检查文件头/魔数、默认拒绝可执行格式、重定向主机、上游 `Content-Disposition`/文件名、平台 `inline/attachment` 策略、`nosniff`、缓存命中后的权限复核和引用撤销清理。
- 对来源主机、分页链接、媒体下载和回调分别验证 DNS rebinding、IPv4-mapped IPv6、私网/回环/云元数据、端口越界、HTTPS 降级和代理绕过；未通过解析后校验不得上线。
- 按认证 provider 验证缺失/错误/过期凭证、签名原文和重试重新认证；签名 provider 还要验证 constant-time 比较、nonce/时间窗（如适用）和双环境密钥隔离。
- 超大压缩/解压响应、JSON 深度/字段数、重复 key 和非法数值被拒绝或截断为明确状态，不得在内存中无限读取。
- 数据集测试、页面预览和已发布运行使用同一响应映射；草稿/停用数据集不能被正式运行页面读取。
- 在约定 QPS、行数和响应体大小下，连续运行一个完整观察窗口，成功率、延迟和错误率达到项目确认的目标值。
- 若接口要求 POST 请求体、分页或签名，验收必须使用真实契约样例验证，不能仅用连接测试 GET 代替。

### 4.8 取数模式和建议基线

实施前要先决定数据是“按页面即时查询”还是“平台定时采集后查询”。即时查询适合只看当前状态的页面；需要历史趋势、来源短时不可用仍可展示、或第三方接口有严格限流时，应增加平台采集任务和快照表。未实现分页、缓存或快照时，必须在来源适配评审中写明返回范围、完整性限制和 `STALE/TRUNCATED` 展示规则，不能默认为全量数据。

以下是便于立项和联调的建议基线，数值仍需结合第三方 SLA 确认：

| 项目 | 建议首期值 | 当前实现 |
| --- | --- | --- |
| 单次请求超时 | 10 秒（可按数据集调整） | 有数据集超时字段 |
| 响应体上限 | 按字节配置（建议起始值 512 KiB；压缩前后口径写入契约） | 新 endpoint 执行器使用字节上限流式中止并请求 `identity` 编码；压缩响应尚未开放 |
| 返回行数上限 | 按来源配置（建议起始值 1000 行） | 新 endpoint 执行器最多 1000 行，超限返回 `TRUNCATED` |
| 页面刷新周期 | 按来源和页面时效配置（建议从 30 秒起） | 已实现 |
| 瞬时错误重试 | 仅对幂等请求按状态白名单有限重试，指数退避带抖动；每次按认证 provider 重新生成认证材料，签名 provider 才重签名 | 新 endpoint 执行器已实现最多 4 次有限重试；本地回归已验证动态 HMAC 在重试时重新生成时间戳和签名 |
| 短期缓存/快照 | 按来源时效配置；缓存命中显示抓取时间，失败回退标记 `STALE` | 已有跨实例加密原始快照及有界过期回退；媒体候选每次投影重新签发，不作为缓存结果重复下发 |
| 分页/游标 | `NONE/PAGE/CURSOR/LINK` 受控模式，限制最大页数、循环检测、去重键和部分结果状态 | 需补齐 |
| 断路和限流 | 按来源维护并发舱、速率、失败阈值和恢复窗口 | 使用 Redis 共享来源速率、并发配额和断路状态；依赖部署实例连接同一 Redis |

分页、重试和缓存必须由 endpoint 取数 profile 明确，不得依赖前端自行拼接：

- `NONE`：记录来源返回范围、排序和完整性限制，只能作为有限快照使用；
- `PAGE`：登记页码/大小参数、起始值、总数或下一页条件，达到最大页数、空页或重复页即停止；
- `CURSOR`：登记游标字段、初始游标、下一游标路径、最大页数和游标持久化策略；
- `LINK`：只跟随契约允许的下一页链接，并重新校验主机、协议和端口；
- 所有模式都要检测循环、限制累计行数/字节数、按业务键去重并记录 `partial`/`truncated`；来源不支持一致性快照时，页面须显示抓取批次和可能的跨页漂移。

重试策略至少登记可重试状态、最大次数、最小/最大退避、总时间预算和抖动；解析 `Retry-After` 时限制其上限。401/403、参数校验、schema 错误和非法媒体不得盲目重试；POST 或媒体请求只有来源确认幂等/无副作用时才可自动重试。每次重试按认证 provider 重新生成认证材料，签名 provider 才重新生成时间戳、nonce 和签名。连续失败达到阈值后进入 `CIRCUIT_OPEN`，按恢复窗口探测，恢复后再放量。

缓存键至少包含 `sourceCode + endpointCode`、规范化参数、认证策略/凭证版本、schema 版本、环境和租户/页面/分享受众范围，并在命中时再次校验授权；敏感结果不得进入公共 CDN。缓存命中返回原始 `requestId`、抓取时间和 TTL；来源失败时是否允许 `stale-if-error`、允许多久以及页面如何显示 `STALE`，必须由来源和业务负责人确认。

来源停用、凭证失效或接口升级时，管理员应能保留上次成功快照供人工比对；是否允许页面继续展示过期快照、过期多久以及标记方式必须由业务负责人确认。

运维视图至少显示来源最后成功时间、最近业务时间、最近耗时、连续失败次数、最近质量状态和最近 `requestId`；连续失败、长期无数据或业务时间明显滞后时按来源联系人告警。

## 5. 场景二：我方提供接口，第三方主动推送

### 5.1 目标和适用范围

外部系统在业务事件产生、快照完成或文件通知产生后调用驾驶舱的入站接口。驾驶舱先完成安全校验和可靠接收，再异步标准化、入库和发布给数据集及实时页面。接口应返回明确回执，使外部系统知道一批数据是已接收、重复、拒绝还是需要重试。

首期建议采用 HTTPS `POST` JSON；MQ、SFTP、文件交换和长连接双向协议作为独立适配器，不与通用推送接口混用。

每个入站 endpoint 必须选择一个 payload profile，并以该 profile 冻结字段和状态：

| profile | 适用内容 | 关键标识和语义 |
| --- | --- | --- |
| `EVENT` | 事件流或事件批次 | `eventId`、业务发生时间、`operation`；支持幂等更新 |
| `SNAPSHOT` | 指标、库存、人员/设备当前快照 | `snapshotId`、`snapshotTime`、替换或合并范围；不强制事件字段 |
| `RECORD` | 通用记录批量 | `recordId`、记录版本或更新时间；项目范围按来源配置 |
| `FILE_NOTIFICATION` | 文件或媒体到达通知 | `fileId`、平台签发的 `mediaRef`、摘要和下载策略；外部 URL 一律拒绝 |

以下请求体和回执以 `EVENT` profile 为示意，不是所有来源的强制 schema。`projectCode`、`tenantCode`、业务来源标识和事件类型按来源登记为必填或可选。

### 5.2 业务流程

1. 平台为外部系统建立入站接入方、环境范围、接口版本和凭证。
2. 双方确认 payload profile、批量大小、顺序、重复、修正/删除和重试规则。
3. 外部系统按认证 provider 完成认证并提供约定的幂等标识，调用平台入站接口。
4. 平台在入口层按认证 provider 校验 TLS、接入方、时间戳/随机数/签名（如适用）、内容长度和请求格式。
5. 平台按 profile 校验租户/项目范围、版本、必填字段、类型、枚举和业务时间、快照时间或文件元数据（如适用）。
6. 平台以规范化幂等标识和 profile 定义的业务主键判断重复；在 inbox/outbox 事务或等价的持久队列中可靠写入合法原始报文。
7. 只有在数据库提交或可靠队列确认完成后才返回成功回执；标准化和业务表写入可异步完成，不能先回执再落盘。
8. 消费者转换字段、执行脱敏和业务校验，更新处理状态；失败记录进入重试队列或死信。
9. 数据集从标准化表读取；需要实时展示时发布内部更新通知，平台 WebSocket 向页面推送统一结果。
10. 运维查看接收量、处理延迟、失败和死信，并可按权限重放或作废。

#### 接入方登记字段

平台应为每个外部系统建立独立的接入登记，不把接入方直接等同于页面数据集：

| 字段 | 要求 |
| --- | --- |
| `integrationCode` / 名称 | 入站命名空间内唯一、创建后不可变；名称、合作方和联系人可维护 |
| 环境 | 沙箱、测试、生产分别登记，凭证和数据存储隔离 |
| 项目/组织范围 | 按来源配置为必填或可选；请求体范围必须与登记范围相交 |
| profile/类型/版本 | 允许的 payload profile、业务类型（如 `eventType`）、`schemaVersion` 和映射版本 |
| 认证 | `keyId`、认证方式、密钥引用、创建/过期/吊销时间；密钥只显示一次 |
| 网络策略 | 允许的 IP/CIDR、TLS 要求、网关入口和来源联系人 |
| 容量策略 | 单批条数、请求体大小、QPS、并发数和日配额 |
| 数据策略 | 时区、敏感字段、原始体留存期、迟到/修正/删除规则 |
| 状态 | `DRAFT`、`ACTIVE`、`PAUSED`、`REVOKED`；停用后新请求拒绝，历史台账保留 |

管理端应支持维护“源字段 → 标准字段”的映射和版本、测试报文 dry-run、启用/暂停、双密钥平滑轮换、立即吊销和最近使用时间查看。接入方管理、死信重放和密钥操作应与普通数据集编辑权限分开。

### 5.3 入站接口建议

接口路径示例（实际路径由 endpoint profile 登记；`events` 只是示例名称）：

```http
POST /open-api/v1/integrations/{integrationCode}/events
```

路径中的 `integrationCode` 是入站认证和授权的权威接入方标识。请求体中的 `sourceCode` 仅在 payload profile 或业务契约需要时使用；若同时出现，必须与登记的映射一致，不能覆盖路径身份。接口应由独立的开放接口安全链路保护，不直接复用后台 JWT。

入站推送默认禁止 `NO_AUTH`；即使通过专网或 IP 白名单接入，也必须绑定可轮换的 API Key、Bearer、HMAC、mTLS 或等价的网关认证 provider。provider、版本和密钥由服务端登记，客户端不能在请求中选择认证方式。

#### 请求头

| 请求头 | 要求 |
| --- | --- |
| `Content-Type` | `application/json`；是否允许 gzip 需在接入登记中配置，并同时限制压缩前后大小 |
| `X-Integration-Id` | 可选的接入方标识；出现时必须与路径 `integrationCode` 一致 |
| `X-Schema-Version` | payload profile 对应的模型版本，例如 `1.0`；是否必填按 profile 登记 |
| `X-Key-Id` | 密钥轮换时的认证主体标识；必须属于该 `integrationCode` 的已启用密钥，并按 provider 规则参与校验 |
| `X-Timestamp` | 仅在认证 provider 要求时出现；每个接入方固定选择 Unix 秒或 RFC 3339 之一 |
| `X-Nonce` | 仅在认证 provider 要求时出现；单次随机串，用于防重放 |
| `X-Signature` | 仅在签名 provider 要求时出现；按登记的原文和编码生成 |
| `Idempotency-Key` | 批次幂等键，默认必填；若契约允许省略，必须由受控的 `batchId/messageId` 或 profile 批次键派生规范化标识，缺失或无法唯一派生时拒绝 |
| `X-Request-Id` | 外部请求追踪号，平台限长、限字符并原样关联但不盲目信任；平台始终生成自己的不可预测 `requestId` |
| `Authorization` | 若采用 API Key/Bearer，按双方确定的方式使用 |

以下签名原文仅作为 HMAC 类认证 provider 的示意；实际路径、查询串、压缩和正文范围必须按接入方契约登记。推荐将身份、版本和幂等标识也绑定到签名：

```text
HTTP_METHOD + "\n" + REQUEST_TARGET + "\n" + integrationCode + "\n" + X-Key-Id + "\n" + X-Timestamp + "\n" + X-Nonce + "\n" + NORMALIZED_IDEMPOTENCY_KEY + "\n" + X-Schema-Version + "\n" + SHA256(REQUEST_BODY)
```

`REQUEST_BODY` 必须是验签前读取的原始字节，不能用重新序列化后的 JSON 替代。双方必须冻结 `REQUEST_TARGET` 采用原始 request-target 还是唯一的规范化形式，并明确 query 排序、百分号编码、重复斜杠、点段、Unicode、压缩前/后的 body、换行和空白规则；网关与应用使用同一解析规则，遇到歧义编码、重复安全头或非法控制字符直接拒绝。环境、主机/SNI 和 endpoint 必须绑定到接入登记或签名范围，避免跨环境重放。不能只约定“做签名”而不约定验签原文。若请求头与请求体同时携带接入方或版本信息，路径 `integrationCode` 和 endpoint 登记为权威值，其他副本必须一致，否则拒绝。

接收台账保存规范化幂等标识（`Idempotency-Key` 或 profile 明确的批次/业务键）、`bodyHash`、首次接收时间、平台 `requestId`、原回执和过期时间。`bodyHash` 必须按认证 profile 约定的 wire 原始字节或解压后字节计算，并同时用于签名（如适用）和冲突判断；同一标识与相同摘要返回原回执或当前 `PROCESSING`，相同标识与不同摘要返回 `409 CONFLICT`。nonce 只有在签名和时间窗验证成功后才可通过原子 check-and-set 消费，去重范围至少包含 `environment + integrationCode + 认证主体（keyId、证书指纹等） + nonce`，保存时间覆盖允许的时间窗和外部最大重试窗口。无 nonce 的 API Key/Bearer/mTLS provider 必须登记等价的重放控制（短期令牌、证书轮换、幂等台账或网关策略）。

建议首期固定以下安全和容量基线，正式值在接入登记时可按来源下调或经审批上调：

| 项目 | 建议基线 |
| --- | --- |
| 时间戳有效窗口 | 收发时间相差不超过 300 秒 |
| nonce 防重放 | Redis 或等价缓存保存至少 10 分钟，重复 nonce 直接拒绝 |
| 单批条数 | 不超过 500 条 |
| 单请求体 | 不超过 1 MiB（压缩前后口径要写入契约） |
| 单接入方限流 | 默认 10 请求/秒、并发 20，可按接入方配置 |
| 平台内部重试 | 瞬时失败最多 3 次，指数退避并带抖动 |
| 死信阈值 | 单条消息/记录连续失败 5 次后进入死信 |
| 原始数据保留 | 建议 30–90 天，按敏感等级和合规要求确认 |

网关和应用层都要限制请求体、解压后大小、JSON 深度、字段数量、数组长度、字符串长度和单条嵌套大小；采用流式读取/摘要，拒绝解压炸弹、重复 JSON key、`NaN/Infinity`、未知认证算法和认证降级。验签比较使用 constant-time，签名校验、nonce 消费和幂等台账写入的顺序必须在实现和测试中固定。入站 API 默认关闭 CORS；`Origin` 白名单只能限制浏览器访问，不能替代服务到服务认证。

外部 `integrationCode`、`messageId`、`requestId`、幂等键和业务主键必须设置最大长度、允许字符集和控制字符规则，拒绝 CR/LF 及日志注入；结果查询按 `environment + integrationCode` 鉴权并采用不可枚举标识或额外权限校验，不能仅凭可猜的消息 ID 读取状态。

#### 请求体

推荐使用批次信封，兼容单条/批量消息或记录（具体由 profile 定义）：

```json
{
  "messageId": "partner-message-20260908-0001",
  "retryOf": null,
  "requestId": "partner-request-20260908-0001",
  "sourceCode": "external-system",
  "projectCode": "project-001",
  "schemaVersion": "1.0",
  "sentAt": "2026-09-08T10:00:00+08:00",
  "items": [
    {
      "eventId": "E10001",
      "eventType": "ATTENDANCE",
      "operation": "UPSERT",
      "occurredAt": "2026-09-08T09:58:00+08:00",
      "sequence": 10001,
      "data": {
        "personId": "P001",
        "direction": "IN",
        "location": "GATE-A",
        "status": "NORMAL"
      }
    }
  ]
}
```

profile 规则：

- 信封中的 `messageId`、`schemaVersion` 和 `items` 是否必填、`messageId` 的唯一范围及批次是否允许为空，由 endpoint profile 冻结；`retryOf` 仅用于关联子集/修正重试，必须引用已存在的批次标识；`integrationCode` 由路径/认证接入方确定，不以请求体覆盖。
- `EVENT` profile 至少定义事件主键、业务发生时间和操作类型；`SNAPSHOT` profile 至少定义快照主键、快照时间和替换/合并范围；`RECORD` 与 `FILE_NOTIFICATION` 按各自 schema 定义业务主键和版本。
- 项目、租户、组织和事件类型字段按接入登记为必填或可选；出现于多个位置时必须一致。
- 未定义字段应按版本策略拒绝或忽略，不能静默改变字段含义；每个 profile 明确必填字段、空值、枚举和行级错误策略。
- 单批原始请求体、单条记录和嵌套字段大小均有限制；超限直接拒绝并返回可重试性说明。

#### 回执

平台在数据已经可靠落盘或进入持久队列后返回：

```json
{
  "code": "ACCEPTED",
  "message": "已接收",
  "messageId": "partner-message-20260908-0001",
  "requestId": "platform-request-001",
  "integrationCode": "external-integration",
  "accepted": 1,
  "processing": 0,
  "duplicates": 0,
  "rejected": 0,
  "retryable": 0,
  "items": [
    { "eventId": "E10001", "status": "ACCEPTED" }
  ]
}
```

建议状态码和处理方式：

| HTTP 状态 | 含义 | 外部系统动作 |
| --- | --- | --- |
| `202` | 已可靠接收，异步处理中；`code` 为 `ACCEPTED`、`PROCESSING` 或契约约定的 `PARTIAL` | 等待回执丢失时使用同一规范化幂等标识查询或重试；不得生成新标识 |
| `200` | 同步处理完成（仅在契约明确时使用）；可返回 `ACCEPTED`、`COMPLETED` 或 `PARTIAL` | 记录逐条结果 |
| `400` | JSON、字段、版本或业务校验失败 | 修正后生成新的规范化幂等标识再发 |
| `401/403` | 凭证、签名、来源或范围失败 | 先修复认证/授权，不重试原请求 |
| `409` | 幂等标识内容冲突或版本冲突 | 查询原请求结果，不能盲目覆盖 |
| `413` | 请求体过大 | 拆分批次 |
| `415/422` | 内容类型或字段业务规则不符合契约 | 按错误明细修正后再发 |
| `429` | 平台限流 | 遵守 `Retry-After`，指数退避 |
| `500/503` | 平台暂时不可用 | 保留同一规范化幂等标识重试 |

`429`、`500` 和 `503` 响应应返回 `Retry-After`（若能计算），错误体统一包含稳定错误码和 `requestId`，不返回密钥或完整原始报文。

逐条处理的部分成功必须在回执中同时给出 `accepted`、`processing`、`duplicates`、`rejected` 和可重试项明细；异步场景使用 `202 + code=PARTIAL/PROCESSING`，同步场景仅在全部项处理完成后使用 `200 + code=PARTIAL`。完全相同的原始报文重试才可继续使用原规范化标识；只重试子集或修正内容时必须生成新的批次标识，并携带 `retryOf` 指向原批次，同时保留 profile 业务键。网络/限流/平台暂时失败在原报文未改变时继续使用原标识，避免以新标识绕过幂等约束。

### 5.4 可靠性和一致性要求

#### 批次原子性

- 信封级错误（认证校验（如 provider 适用）、版本、JSON、接入方范围、批次大小）导致整批拒绝，不写入任何业务记录。
- `EVENT` profile 的单条字段错误、`SNAPSHOT/RECORD` 的单条记录错误和文件通知错误，允许按接入方配置“整批拒绝”或“逐条处理”。逐条处理时，合法项进入队列，错误项在回执中标记 `REJECTED` 并附稳定错误码。
- 对部分成功批次，外部系统可只重试被拒绝或暂时失败的项，但子集报文必须使用新的批次规范化幂等标识并通过 `retryOf` 关联原批次；同一批次的原报文重试才继续使用原标识，不能通过新标识静默覆盖已有业务键。

#### 幂等

- 按 `environment + integrationCode + profile 定义的业务范围 + businessKey` 建立可配置的唯一约束；`EVENT` 使用 `eventId`，`SNAPSHOT` 使用 `snapshotId`，`RECORD` 使用 `recordId`，文件通知使用 `fileId` 或来源摘要。
- 批次按 `environment + integrationCode + endpoint + normalizedIdempotencyKey` 建立幂等约束；`normalizedIdempotencyKey` 来自 `Idempotency-Key` 或契约明确的批次/业务键，缺失且无法唯一派生时拒绝。幂等台账保留期至少覆盖外部系统最大重试窗口，并使用数据库/缓存原子唯一约束处理并发重复。
- 相同业务键重复投递应返回 `DUPLICATE` 或原处理结果，不能生成第二条标准化记录；相同规范化幂等标识但 body hash 不同返回 `409 CONFLICT`，相同标识且摘要相同返回原回执或 `PROCESSING`。
- 本模型提供“至少一次投递 + 幂等效果”，不对外宣称 exactly-once 传输。

#### 顺序和迟到

- 默认不承诺跨请求顺序；`EVENT` 若业务依赖顺序，使用 `sequence`、分区键或业务时间窗口明确处理。
- `EVENT` 迟到项按 `occurredAt` 入账，另记录 `receivedAt`；`SNAPSHOT` 按 `snapshotTime` 判断新旧；是否允许回补历史日期由业务规则决定。
- `EVENT/RECORD` 的校正和删除必须使用显式操作类型和版本号；`SNAPSHOT` 明确替换/合并范围；所有变更保留原始消息和审计关联。

#### 重试和死信

- 外部系统只对网络失败、`408`、`429`、`5xx` 重试；`4xx` 参数/认证错误先修复后再投递。
- 平台必须保证回执发出前数据已可靠保存；无法落盘时返回 `5xx`，让外部系统在原报文不变时保留同一规范化幂等标识重试。
- 消费失败按指数退避重试，达到上限后进入死信；死信保留原因、最后一次错误、原始请求引用和重放次数。
- 人工重放必须有权限、审批或操作备注，并再次执行幂等检查。

### 5.5 建议的数据模型

实际表名可按项目命名规范调整，逻辑上至少需要以下对象：

| 对象 | 关键字段 | 用途 |
| --- | --- | --- |
| 接入方 | `integrationCode`、名称、环境、状态、项目范围、认证方式、密钥引用、版本 | 管理第三方身份和授权 |
| 接入接口 | 路径、协议、允许方法、限流、批量上限、当前版本 | 管理入口契约 |
| 接收批次 | 幂等键、外部请求号、请求摘要、接收时间、状态、计数 | 记录一次投递和回执 |
| 原始消息 | 接入方、profile 业务主键、业务时间/快照时间/文件元数据、原始体引用或脱敏副本、内容摘要、版本 | 保留可追溯原始证据 |
| 标准化数据 | 标准字段、处理状态、来源业务主键、更新时间 | 供数据集和页面查询 |
| 投递/处理日志 | 阶段、尝试次数、耗时、错误码、`requestId` | 监控和排障 |
| 死信 | 原始消息引用、profile 业务主键、失败原因、重试次数、处理人、处理时间 | 失败隔离和重放 |

接收批次和消息状态建议至少覆盖 `RECEIVED`、`VALIDATED`、`PROCESSING`、`RETRYING`、`ACCEPTED`、`DUPLICATE`、`REJECTED`、`CONFLICT`、`FAILED`、`DEAD_LETTER`、`CANCELLED`；状态迁移和允许的人工操作要写入接口及运维说明。

原始体默认不完整保存；是否保留完整报文、保存多久以及哪些字段必须脱敏由业务和合规要求确认。确需保存时，敏感字段逐字段加密，原始体、备份和死信使用独立权限并执行到期删除审计；否则至少保存不可逆摘要和足够的字段级追踪信息。

### 5.6 下游数据集和实时页面

- 标准化数据表通过 SQL 数据集提供快照、统计和历史查询；数据集字段与接收契约解耦，外部版本变化通过标准化映射吸收。
- 页面组件继续只绑定数据集，不直接读取入站表或消息队列。
- 若要求秒级或准实时展示，消费成功后发布内部更新通知，由平台 WebSocket 向已授权页面推送；浏览器永远不直接连接第三方推送端点。
- WebSocket 推送失败不回滚已接收消息；页面可通过刷新标准数据集补齐结果。
- 页面应显示来源状态、最后接收时间、处理延迟和数据质量，而不是只显示一组数字。

### 5.7 处理结果查询和通知

异步接收返回 `202` 时，平台至少提供一个受鉴权保护的处理结果查询入口，供外部系统按 `batchId/messageId`、`requestId` 或 profile 业务主键查询批次和逐项状态，例如：

```http
GET /open-api/v1/integrations/{integrationCode}/messages/{messageId}
```

查询结果应包含接收状态、处理状态、成功/重复/拒绝数量、最后错误和更新时间，不返回原始敏感报文；接收批次应持久化原回执。是否增加平台主动回调、回调签名和回调失败重试，作为双方可选能力。回调地址只能由管理员在接入登记中配置，不能来自请求体或业务字段；回调同样执行协议/主机/IP 白名单、逐跳 SSRF 和签名校验，默认不跟随重定向。没有回调时，外部系统以查询接口和原始回执为准。

### 5.8 部署、版本和数据生命周期

- 入站路径由 Nginx/WAF 或同等网关转发到后端，单独配置 TLS、请求体上限、超时、IP/CIDR 白名单和限流；不能直接暴露管理端口。
- 沙箱、测试和生产使用不同的 `integrationCode`、密钥、数据库/队列和回调地址；测试报文支持 dry-run，不能污染生产标准数据。
- 接入方同时维护当前和上一兼容版本；未知版本返回稳定错误码。版本升级先登记 schema 和映射，再切换生产流量。
- 原始接收台账、标准化数据、处理日志和死信分别定义保留期、归档和删除策略；删除敏感原始体后仍保留消息摘要、状态和审计关联。
- 备份恢复演练需验证接收台账唯一键、未处理队列、死信和密钥引用可恢复，恢复后不会重复消费。

### 5.9 场景二验收标准

- 各已登记 profile 的合法单条和批量请求可在约定时限内收到成功回执，回执包含平台 `requestId` 和逐批/逐项计数。
- 信封级错误（错误 JSON、未知版本、缺少必填范围、过期时间戳/重复 nonce/错误签名（按认证 provider 适用）和超大请求）被拒绝且不产生业务记录；逐项校验失败按契约返回部分结果，不得误报整批成功。
- 重复投递不产生重复标准化数据；同一 profile 业务键或同一规范化幂等标识内容变化会进入冲突或死信，不静默覆盖。
- 平台在数据库或可靠队列不可用时返回可重试状态；原报文不变时，恢复后使用同一规范化幂等标识重试可以安全完成。
- 处理失败进入有限重试和死信；运维可查询、授权重放并获得审计记录。
- 标准化数据能被数据集读取，字段、时间和范围正确；需要实时展示时，页面收到消息结果的延迟达到项目确认目标。
- 重启应用、消费进程或消息组件后，已接收但未完成的数据不丢失，状态可以继续处理。
- 监控能够按接入方查看接收量、成功率、重复率、拒绝率、处理延迟、队列积压和死信数量，并按阈值告警。
